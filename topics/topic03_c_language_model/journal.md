# Тема 03 — Personal Learning Log

## День 10 изучения темы

Сегодня продолжили изучение модели языка C и разобрали связь между типами, смыслом данных и их представлением в памяти.

Начали с вопроса:

> Могут ли два объекта разных типов иметь абсолютно одинаковые байты в памяти?

Сначала возникло предположение, что информация о типе может находиться в машинном коде. Затем стало понятно, что процессору не требуется знать типы C: он получает машинные инструкции и данные и выполняет указанные ему операции.

После этого рассмотрели роль компилятора. Тип необходим ему для того, чтобы понимать смысл данных и определять допустимые операции над ними.

Для проверки этой идеи провели мысленный эксперимент с языком без типов. Если оставить только память и байты, компилятору необходимо каким-либо другим способом сообщать, что конкретные данные являются числом, текстом и т. д. Иначе невозможно определить смысл операции над ними.

В результате пришли к промежуточному выводу:

> Типы нужны компилятору для того, чтобы определять смысл полученных данных и допустимые операции над ними.

После этого вернулись к вопросу об одинаковых байтах. Было предположено, что два объекта разных типов действительно могут иметь одинаковое физическое представление в памяти, поскольку сами байты не содержат обязательной информации о типе.

Полезной аналогией стала картинка с числом 6/9: само изображение не меняется, но его смысл зависит от контекста, в котором оно рассматривается.

Главный вывод занятия:

> Одни и те же байты сами по себе не обязаны определять смысл данных. Тип и контекст программы позволяют компилятору понимать, как эти данные следует интерпретировать и какие операции над ними допустимы.

Пока не переходили к сложным деталям представления типов, ABI, aliasing и другим понятиям. Их изучение оставлено на более поздний этап.

Следующий шаг — проверить сформированную модель на реальном C-коде.
# Тема 03 — Personal Learning Log

## День 11 изучения темы

Продолжили исследование представления данных в памяти и вернулись к вопросу:

> Могут ли два объекта разных типов иметь абсолютно одинаковые байты в памяти?

Сначала сформулировали гипотезу, что для ответа недостаточно просто посмотреть на байты: необходимо учитывать их интерпретацию и контекст программы.

Провели практический эксперимент с:

```c
int a = 1;
unsigned char *p = (unsigned char *)&a;
```

Через `p[0]`, `p[1]`, `p[2]` и `p[3]` посмотрели отдельные байты объекта `a`.

На используемой системе получили:

```text
1
0
0
0
```

Эксперимент был повторён около 20 раз, результат оставался одинаковым.

После этого заменили значение на:

```c
int a = 257;
```

Получили:

```text
1
1
0
0
```

Перед вторым экспериментом самостоятельно перевели `257` в двоичную систему и пришли к прогнозу:

```text
p[0] = 1
p[1] = 1
p[2] = 0
p[3] = 0
```

Результат полностью совпал с прогнозом.

На основании двух экспериментов установили поведение используемой системы:

> Младший байт многобайтного значения располагается по меньшему адресу.

После этого познакомились с термином `little-endian`.

Важно: вывод сделан именно для исследованной системы. Эксперимент не доказывает, что любой `int` на любой платформе будет иметь такое же представление.

Затем вернулись к первоначальному вопросу о типах.

Было замечено, что при преобразовании:

```c
unsigned char *p = (unsigned char *)&a;
```

сами байты объекта `a` не изменяются. Мы лишь получили возможность обращаться к той же области памяти как к последовательности байтов.

Из этого сформировали важное наблюдение:

> Одинаковые байты сами по себе не обязаны определять смысл данных. Для их интерпретации важен контекст программы и информация о типе.

Также обсудили, что для восстановления значения многобайтного объекта из последовательности байтов необходимо знать как минимум, как эти байты интерпретируются и в каком порядке они расположены.

Главный результат дня:

```text
байты
 ↓
представление
 ↓
контекст / тип
 ↓
интерпретация
 ↓
значение и допустимые операции
```

Следующий возможный шаг — проверить, что произойдёт, если не просто читать отдельные байты объекта, а изменить один из них.

## День 12 изучения темы

Например:

```text
11111110

unsigned → 254

После этого начали новый блок — указатели.

Отправной точкой стало уже известное свойство объекта: у объекта есть адрес.

Рассмотрели:
int a = 42;
и идею сохранения адреса объекта:
int *p = &a;
Сформировали базовую модель:
a
↓
объект, содержащий значение

&a
↓
адрес объекта

p
↓
объект, содержащий этот адрес

*p
↓
объект, находящийся по адресу, сохранённому в p

Таким образом, указатель позволяет не только хранить адрес объекта, но и обращаться к объекту через этот адрес.

Связали новую тему с предыдущими экспериментами:
unsigned char *p = (unsigned char *)&a;

Этот код уже был фактическим использованием указателя для доступа к представлению объекта a через отдельные байты. Теперь начали разбирать механизм указателей непосредственно.

Главный вывод занятия:

Указатель — это объект, содержащий адрес другого объекта; разыменование позволяет обратиться к объекту по сохранённому адресу.

На этом этапе синтаксис указателей изучался только на базовом уровне. Арифметика указателей, массивы и более сложные правила будут разобраны отдельно.
